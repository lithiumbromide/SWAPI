# SWAPI corpus maintainer
The repository turns the SOLIDWORKS API CHM help into Markdown (`markdown/`), a navigation index (`llm_index/`) and the bundled data of two distributable skills. Every artifact is generated by a script in `scripts/`, so all work here means changing a script or its configuration and regenerating, then proving the result with counts, diffs and evals.
## Repository map
| Path | Tracked | Produced by |
| --- | --- | --- |
| `api/` (CHM input), `extracted/`, `API_HTML/` | no | user, unpacker, `collect_html.py` |
| `markdown/` | yes | `convert_sw_api_docs.py` |
| `llm_index/` | yes | `build_llm_index.py` |
| `.claude/skills/*/data/`, `.claude/skills/*/scripts/swapi.py`, `LICENSE.txt`, `NOTICE.md` inside skills | yes | `build_skill_data.py` |
| `.claude/skills/*/SKILL.md`, `references/`, `assets/`, `evals/` | yes | hand-written |
| `scripts/`, `scripts/skill_runtime/`, `scripts/skill_data.json` | yes | hand-written single sources |
| `dist/`, root `*.zip` such as `api-docs.zip`, `.venv/` | no | packager, downloads, venv |
## Environment
- Windows: use the project interpreter `.venv/Scripts/python.exe` (create it with `py -3 -m venv .venv` and `pip install -r requirements.txt`), because the scripts need the packages in `requirements.txt` and `run_pipeline.ps1` runs that interpreter; on Linux use `python3` with the same requirements. `python` in the commands below means this interpreter.
- CHM extraction needs 7-Zip on Windows (`7z.exe` on `PATH` or `C:/Program Files/7-Zip/7z.exe`) and `extract_chmLib` elsewhere, because the unpackers shell out to them.
- The main checkout lives under OneDrive with a long root and the corpus has very long file names ([quirks](references/converter-quirks.md#modules-and-paths)), so create worktrees and temporary corpora under a short root (a few folders below the drive) and keep `git config core.longpaths true`, because many Windows tools fail at 260 characters.
- Pause OneDrive sync during full regenerations, because about 54,000 files are rewritten and sync locks cause access-denied errors.
- Run PowerShell scripts as `powershell -ExecutionPolicy Bypass -File <script>`, because script execution is often disabled.
## Pipeline
Run from the repository root and check each stage before starting the next, because a silent partial stage poisons every later artifact. Commands, parameters, expected counts and recovery are in [pipeline.md](references/pipeline.md).
1. Save the current state: `git show HEAD:llm_index/manifest.json > <temp>/manifest-old.json` and export the current skill data with `git archive HEAD .claude/skills` into a temporary folder.
2. Unpack, collect, convert, index: on Windows `powershell -ExecutionPolicy Bypass -File scripts/run_pipeline.ps1 -ApiVersion 2026 -CleanExtract`; stage by stage or on Linux as in [pipeline.md](references/pipeline.md#windows-stage-by-stage). Smoke-test the converter with `--limit 20` into a temporary folder first whenever it changed.
3. Compare: `python scripts/compare_index.py <temp>/manifest-old.json llm_index/manifest.json` and explain every module whose count moved by more than a few percent.
4. Skill data: `python scripts/build_skill_data.py --previous <exported data>`; read its warnings and the `changes.tsv` counts.
5. Validate: `python scripts/package_skills.py --validate-only` until it passes.
6. Evals and packaging when the change affects skill behaviour or a release is due ([skills-release.md](references/skills-release.md)).
## New SOLIDWORKS release
1. Work on branch `integration` (or a feature branch merged into it), because `main` must always hold a corpus that matches its skill data.
2. Put the new CHM files into `api/` and run the pipeline with `-CleanExtract`, because the unpacker skips CHM files it extracted for the previous release.
3. Detect new modules from `compare_index.py` or `llm_index/modules.json` (2026 adds `swvisualizeapi` and `swvisualizeapiVB6`; module names are case-sensitive) and verify each is assigned to a skill or listed in `exclude_modules` in `scripts/skill_data.json`, adding it only if missing, because the generator refuses unassigned modules.
4. Rebuild skill data with `--previous` and review `changes.tsv`: added members, newly obsoleted members, removed members; report counts per kind and the notable interfaces.
5. Update `metadata.sw-api-version` and `metadata.version` of both distributable skills and the version strings in `README.md`, `NOTICE.md` and `AGENTS.md`.
6. Rerun both skills' evals and trigger evals on the target models.
7. Open a pull request to `main` with the count deltas, the `changes.tsv` summary, the size table and the eval results; release after merging.
## Converter and index fixes
- Reproduce the defect on one source page, fix the script, verify the page, then regenerate everything downstream (Markdown, index, skill data), because downstream files are never patched by hand. The procedure and every known quirk with its example path are in [converter-quirks.md](references/converter-quirks.md).
- Confirm a fix with a corpus-wide search (for example `rg -l kadov_tag markdown` must return nothing), because spot checks miss pages from other help authoring tools.
- When the fix changes link resolution or symbol kinds, rebuild the index and compare symbol and edge counts, because the generator and the runtime depend on them.
## Skills
- Edit the runtime only in `scripts/skill_runtime/` and module assignments only in `scripts/skill_data.json`, then regenerate, because the copies inside the skills are overwritten and `--check` flags drift.
- Keep `SKILL.md`, references, assets and evals hand-written and the style rule: no code comments or docstrings, every fact in one file, no blank-line padding or separator lines; `package_skills.py --validate-only` enforces it.
- Package with `python scripts/package_skills.py` only after `--validate-only` passes, because a zip built from invalid skills gets uploaded and cached by users.
## Guardrails
- Never hand-edit `markdown/`, `llm_index/`, skill `data/` or runtime copies, because the next regeneration silently reverts the edit.
- Never stage `api/`, `extracted/`, `API_HTML/`, `*.zip` or `dist/`, because they are large, derived from licensed CHM files or reproducible; check `git status --short` before every commit.
- Never build skill data from a partial working tree (many deleted files under `markdown/` in `git status`), because the published data would silently lose modules; restore or regenerate first.
- Never edit other worktrees or the user's OneDrive checkout from a worktree session, because parallel branches share the repository.
- Commit generated artifacts separately from script changes, because reviewers must be able to read the script diff.

## Report format
- Commands run, each with its exit code and the one or two output lines that prove success (counts, `api_version`, `markdown_root`).
- A module count delta table from `compare_index.py` for regenerations, and `changes.tsv` counts for skill data.
- The packager size table (raw MB, zip MB, budget status) whenever zips were built.
- Files changed, grouped as scripts, generated artifacts and skills, and anything left for the user (uploads, releases, OneDrive sync).
